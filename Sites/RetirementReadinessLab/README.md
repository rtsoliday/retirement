# Retirement Forecast - Monte Carlo Simulator for Sites

A browser port of the native Android app in `../../Android/RetirementReadinessLab/`. The web app runs as a static Sites page. Scenarios and calculations stay in the browser; no scenario data is sent to a server. Export JSON to retain plans outside browser storage.

## Verify

Automatic browser saving requires the Web Locks API in a secure context (HTTPS or localhost). A browser without this API can still calculate and export backups, but does not write browser storage.

Numeric edits are saved when committed by leaving the field. Malformed entries keep the previous assumption and show an error. Clearing an important assumption marks it Unknown, preserves its prior numeric value for editing, and blocks calculations until it is resolved; explicitly entering 0 means none. Dollar amounts and calculated budget totals must stay within JavaScript's supported safe-integer dollar range (up to $9,007,199,254,740,991 in magnitude). Invalid budget totals cannot replace applied spending or its home-cost snapshot. A nonfinite simulation state stops the calculation with an error.

Use Node.js 22 or newer. The test runner enumerates test files explicitly, including on Windows. From the repository root:

```bash
npm test --prefix Sites/RetirementReadinessLab
python -m http.server 4173 --directory Sites/RetirementReadinessLab/dist
```

The Node tests include seeded web output snapshots, independent annual rate and cash-flow checks, malformed-import and failed-save cases, and authenticated billing tests with mocked Stripe responses. Billing regression cases cover search delays, outages, cancellation, changed identities, stale responses, and checkout recovery. The browser app remains buildless in `dist/`. `npm run build:sites` packages its files with a small Worker that protects `/admin` and proxies Cloudflare Analytics requests; publish `.sites-build/` as the Sites artifact. The build places the complete browser JavaScript graph in a content-hashed directory. The simulation worker resolves against the same app release, so modules cannot be mixed across deployments. An old open tab whose release is no longer hosted will ask the user to reload if a worker cannot load.

Regression coverage includes even-sized medians, shortfalls between annual observations, final funding/survival endpoints, subscriptions on later Stripe pages, concurrent account-link conflicts, and saved selection after scenario ID repair. ID repair reserves all existing normalized IDs before assigning replacements. Edits made while an unreadable stored backup is protected prompt a warning before closing; the warning clears after an explicit replacement or valid import saves those edits, and remains if a later edit was excluded from an in-flight recovery save. Scatter dots at the final modeled age stay inside the plot after horizontal outcome jitter, while ages outside a zoomed viewport remain clipped.

Spending targets, the 5% spending sensitivity check, and lower-spending comparisons change annual base spending the same way as the editor. Property tax and home insurance stay at the plan's Housing input, so a lower spending amount never also drops that post-sale reduction. Spending targets exclude totals below those retained bills, rounding the minimum upward to a $500 increment. If no feasible amount within the search range reaches the requested readiness, the lab shows "No amount found"; bills above the search ceiling leave no amounts to test. The original plan remains unchanged by exploration. A comparison that would repeat the current plan is reported as already matching instead of being rerun. Partial-year chart spans use the same age scale for drawing, click inspection, zooming, and panning.

Checkout coordination checks pending and completed purchases across all matching verified Stripe customer records, including a directly verified customer hint. Checkout and account linking use the complete paginated Customer List API to discover owned records, rather than eventually consistent Customer Search. A failed or incomplete list blocks the mutation.

Known scaling limit: that List scan reads every customer in the Stripe account, 100 per request and one request at a time, and account linking reads the list at least twice. Checkout and linking time and Worker subrequests therefore grow with the account's total customer count. Expect slower checkouts after a few thousand customers and, eventually, timeouts or the Worker's per-request subrequest cap (50 on the Cloudflare Workers Free plan). Removing the full scan while keeping these read-after-write guarantees needs a strongly consistent ownership index, such as a Durable Object or D1 table keyed by sign-in identity. Existing payment links are reused, extra links are expired, and a history or expiration failure blocks a new purchase. Requests with different customer hints use a deterministic customer order to coordinate through the same purchase generation even when Search returns no records or only some of them. Regression tests cover more than 500 unrelated customer records before an owned paid record.

Billing regression coverage also includes payment completion between the access check and Checkout-history lookup. Every relevant completed purchase is checked through its subscription directly before another purchase is allowed, including payments already marked paid and older purchases behind newer abandoned or ended Checkouts. Account linking expires existing open Checkouts before changing customer associations, stops if expiration races a payment, and retains the paid customer when a completed purchase has not yet appeared in the subscription list. An unresolved payment blocks linking until it is confirmed or its subscription ends. Linking reserves every matching customer through shared Stripe idempotency keys before changing either ownership field, then rechecks purchases that finished during reservation. A rejected competing link cannot attach its paid customer to the other identity. Pending reservations block Checkout until the same linking pair retries and finishes; a losing reservation becomes reusable once a completed conflicting association proves that the rejected pair cannot commit. Completed retries leave customer records usable even if earlier reservation keys have expired. Checkout verifies current ownership before creating a session and again before returning its URL; a session that finishes during linking expires and returns a retry message. Expiration uses a shared idempotency key so both operations can safely retire the same session. Linking retains both verified identities on all matching records for subscription access and billing management. A record already associated with a third identity blocks linking before any changes. Checkout and linking use identical customer-creation parameters and a shared key per sign-in. Linking provisions missing sign-ins and refreshes the owned records, so a first-time purchase cannot create an unlinked paid record after linking. Stripe idempotency conflicts return HTTP 409 with a retry message. A fresh ownership check still blocks conflicting links after Stripe's idempotency retention expires.

## Financial calculation corrections

Mortality is sampled through the full table independently of the maximum modeling age. Annual death probabilities are preserved, with deaths spread across month ends using a constant mortality hazard between birthdays; the first partial year uses only the remaining months. Each age year still consumes one random draw, including the selected death year, so the finer timing does not shift later spouse, care, or market draws. Seeded results can change from the former birthday-only timing. Cash flows stop at the household observation limit or sampled death month. Care probability and onset use sampled death, so changing the limit does not move care or trigger a premature home sale. A path still alive at the limit is censored rather than recorded as dead; its final observed balance is included in ending summaries and balance bands. Tests check the monthly probability distribution, partial years, survivor changes, and care/home-sale timing.

Old browser and Android backups retain their balances. Without Roth history, migration carries forward the previous assumption that opening Roth savings are remaining contributions, assumes a first funding year of 2021 and no past conversions, and marks the history for review in the editor, planning notes, and text report. Users can correct these fields without changing the account total; JSON backups retain all entered history. The sample plans explicitly use $50,000 contributions and 2021 as their first funding year. Zero means a previously unfunded Roth; a future conversion starts its clock. Year numbering for Roth qualification and conversion periods follows the modeled tax years described above.

Required minimum distributions use the IRS Uniform Lifetime Table and birth-cohort starting ages. Ordinary withdrawals satisfy the minimum; unused after-tax proceeds remain in cash, and RMDs are excluded from Roth conversions. The pooled pretax balance is primary-owned, then spouse-owned after the primary death year. Timing follows the modeled retirement-anniversary tax years, using the owner's whole-year starting age and prior modeled year-end balance. Separate spouse accounts, beneficiary-specific tables, calendar-year timing and first-year deferral are excluded. Pre-retirement growth still omits employment taxes and required distributions; the starting retirement balance estimates do not model a full working household's tax return.

A SEPP started before age 59½ protects the entire pretax pool until the later of five years or age 59½. Only the scheduled payment may leave that account, so a spending gap must use other accounts or produces a shortfall even with protected pretax assets remaining. Conversions are blocked during the restriction. This models a maintained series rather than recapture tax and interest on a broken series.

Cash earns 2% annually. Retirement-period interest is ordinary income, affects taxable Social Security and senior deduction phaseouts, fills conversion brackets, and enters Medicare estimates and lookback income. Cash principal withdrawals are not income. The highest Medicare tier includes exactly $500,000 Single or $750,000 joint income, and those thresholds remain frozen through 2027. Starting in 2028, its separate August 2026 inflation base is approximated with the preceding modeled year's cumulative general price index. The individual threshold is rounded to the nearest $1,000 and joint filers use 150% of it. Lower tiers retain their existing 2026-based inflation projection. Both the initial income estimate and the two-year lookback use this schedule. See [Social Security Act section 1839(i)(5)](https://www.ssa.gov/OP_Home/ssact/title18/1839.htm).

Social Security increases only when the cumulative modeled price level exceeds the reference for its last increase. Deflation leaves benefits unchanged, and a subsequent rebound must recover that price decline before another COLA occurs. This also carries forward assumed deflation before retirement. General inflation remains a proxy for CPI-W, with increases on retirement anniversaries rather than the official third-quarter comparison and December timing. See the [SSA COLA formula](https://www.ssa.gov/OACT/COLA/latestCOLA.html). Roth withdrawal ordering follows [IRS Publication 590-B](https://www.irs.gov/publications/p590b), with the entered remaining regular contributions treated as fixed penalty-free basis, and past and modeled conversions tracked separately.

Stock, bond, pre-retirement returns, and both inflation rates now use monthly lognormal factors with the entered compounded annual arithmetic mean and standard deviation. Inflation draws are not clipped. This changes seeded balances and target results relative to the older monthly normal model and Android. Statistical regressions verify compounded means and volatility; independent cash-flow cases verify the tax corrections.

Risk recommendations come from six paired sensitivity comparisons on up to 128 evenly spaced paths from the run. They report changes in shortfall counts, including general inflation, and disclose the sample size and overlapping effects. They do not infer market risk from overall readiness or claim causal attribution. Target screening skips these extra diagnostics.

## Owner traffic dashboard

`/admin` is an owner-only page. The Worker checks the Sites authenticated user ID before serving the page or `/api/admin/traffic`; anonymous visitors are sent through Sign in with ChatGPT. It asks Cloudflare's zone GraphQL API for daily page views and unique IP counts for `retirementforecast.us`. It does not receive or send retirement scenario data. The browser discards superseded requests when the selected date range changes. The daily unique figures cannot be added to produce a distinct total across the period, so the page shows them by day and reports only the daily peak. Cloudflare's zone metrics include traffic on the custom domain and its subdomains, not the separate `chatgpt.site` origin; internal planner tabs are not separate HTML page views.

To activate live figures, create a Cloudflare API token scoped to this zone with **Account Analytics: Read**, with Zone Resources limited to `retirementforecast.us`, then set `CLOUDFLARE_ANALYTICS_TOKEN` as a secret in the Sites environment and redeploy the current version. Never put the token in source files. Cloudflare may delay or limit the available history, especially on free plans.

Subscriptions on a configured Pro price, or carrying the site’s server-written plan/identity metadata (which every site Checkout writes), grant Pro even when prices are incomplete or have been replaced. Stripe Prices cannot be edited, so this keeps existing subscribers on Pro after a price change. Unrelated subscriptions do not grant Pro. Existing billing customers retain Manage billing access even when no subscription grants Pro, including after an abandoned checkout. No local entitlement database or webhook is required.

After verifying a checkout, the browser keeps a customer lookup reference in session storage. Every use requires server-side verification that the current authenticated account owns that Stripe customer, followed by a current subscription check. This avoids Customer Search delays without trusting a browser entitlement. If the referenced customer has no active subscription, the Worker checks the account’s other matching customers before returning Free access or starting Checkout. An unpaid verified reference still provides portal access when search has not indexed it. Unverified checkout references remain in the URL for retry. A transient check failure preserves previously confirmed Pro access for at most five minutes from the last successful check in the current page session. Confirmed cancellation, authentication rejection, or a known account change ends that access immediately. Billing changes never clear completed calculation results; results still need recalculation after a page reload.

Authenticated account identity and the customer reference survive initial and repeated billing outages, including after grace expires. An unknown prior identity is not treated as a changed account. Grace counts from the last successful verification, not the first failure; repeated failures do not extend it. An expiry timer updates the displayed plan and next-run limit without interrupting an ongoing calculation. A successful check cancels that timer, and payment-pending notices update when Pro is confirmed. Explicit account linking includes recent customer lookup hints and verifies each against either of the two authenticated identities before selecting a customer, so a paid customer missing from Stripe Search is retained. Account linking returns the chosen customer reference for an immediate ownership-checked lookup, avoiding search-index delays after metadata updates; checks begun before linking cannot replace that reference.

Google signing-key retrieval failures (network errors, timeouts, non-success responses, or unusable key payloads) return HTTP 503 without asserting an identity or entitlement. Previously verified access can use the same bounded browser grace period. Invalid tokens and tokens whose key is absent from a successfully loaded usable key set still receive HTTP 401. A fresh key set is refetched for an unknown key ID at most once a minute, and concurrent refreshes share one download, so forged tokens cannot force a Google key download on every request while rotated keys still load promptly. Key-service outages do not authorize billing operations, fall back to a different sign-in, or grant Pro to a new page session.

To enable Checkout, create monthly and yearly recurring Prices for the same Pro product in Stripe, configure its billing portal, and set these Sites variables: `STRIPE_SECRET_KEY` (secret), `STRIPE_PRO_MONTHLY_PRICE_ID`, and `STRIPE_PRO_YEARLY_PRICE_ID` (test prices), plus `STRIPE_PRO_LIVE_MONTHLY_PRICE_ID` and `STRIPE_PRO_LIVE_YEARLY_PRICE_ID` (live prices). The Worker selects the matching price pair from the secret key's mode and disables Checkout if that pair is missing. The plan screen offers $9.99 per month and $79 per year; Stripe Checkout confirms the selected price before payment. While the key is in Stripe test mode, Checkout and billing are available only to the signed-in Site owner; other visitors remain on the free preview. The owner keeps complimentary Pro and sees a labeled test-checkout option when no matching active test subscription exists. An existing matching subscription blocks duplicate checkout. Pending purchases are coordinated through Stripe session history and a shared idempotency key across concurrent requests. Repeated requests reuse an open payment link; choosing a different interval expires the earlier link before creating a replacement. A completed payment still awaiting confirmation blocks another purchase. With a live key, complimentary owners cannot start a paid checkout but can manage an existing subscription. With a live key, anonymous visitors can use the Sign in with ChatGPT link before upgrading. The signed-in account can manage its subscription through Stripe Billing Portal. Checkouts, billing status, and portal session creation have server-side authentication; no Stripe secret is included in browser files.

Owner access uses the same Sites-authenticated owner check as `/admin` (owner account ID or authenticated email `rtsoliday@gmail.com`) or a signed Firebase Google token with the known owner UID or that verified email. An anonymous email or unverified Firebase token is insufficient. The owner can use up to 10,000 paths without a Stripe subscription.

Because the Monte Carlo engine is delivered to every browser, a person can edit the JavaScript and run more paths without paying. Keeping all calculation on the user's computer makes that limitation unavoidable. Do not claim that Pro prevents deliberate bypass.

## Google sign-in

Google uses Firebase Authentication, separate from Sites' built-in ChatGPT sign-in. The browser receives only the public Firebase web-app config. The Worker verifies each Firebase ID token's signature, issuer, audience, expiry, and sign-in provider before looking up Stripe; it never trusts an email address as proof that two accounts belong to one person. A customer can explicitly link a ChatGPT sign-in to a Google sign-in in **Plans & billing**. Existing ChatGPT subscriptions remain accessible through ChatGPT until linked. Linking checks every matching customer record, selects the paid customer ahead of abandoned checkout records, and retains both verified identities on the other matching records so concurrent purchases keep their owners. If multiple distinct customer records have active subscriptions, linking stops before changing metadata rather than choosing one. The browser stores the Firebase sign-in session locally; it still stores scenarios locally and does not upload them to Firebase.

To activate Google, create a Firebase project and web app in the [Firebase console](https://console.firebase.google.com/), enable **Authentication → Sign-in method → Google**, and add `retirementforecast.us`, `www.retirementforecast.us`, and `retirement-readiness-lab-web.rtsoliday123.chatgpt.site` to Firebase Authentication's authorized domains. In the Sites environment set these **public** web-app config values from Firebase project settings: `FIREBASE_API_KEY`, `FIREBASE_AUTH_DOMAIN`, `FIREBASE_PROJECT_ID`, and `FIREBASE_APP_ID`. Set `FIREBASE_GOOGLE_ENABLED=true` only after the Google provider and authorized domains are ready. Redeploy the current Site version after changing environment variables.

Test Google sign-in on the custom domain and the `chatgpt.site` origin before relying on it: sign in, start and cancel Checkout, then use a test subscription to verify the 10,000-path entitlement and portal access. Test existing ChatGPT Pro subscribers before and after explicit linking. The Worker token tests use generated signing keys and fake Stripe responses; they do not replace a live provider and Stripe test. If Firebase config is absent, or the Google enabled flag is false, the Google button stays hidden and existing ChatGPT billing continues to work.
